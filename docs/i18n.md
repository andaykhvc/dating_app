# Interface languages (i18n)

The app's interface can be shown in English or Turkish. This is the *interface*
(menus, buttons, messages); the languages people learn are a separate thing
(`content/languages.json`).

## How it works

- **No URL prefix.** The language comes from the person, not the path (`/tr/...`):
  the app sits behind sign-in and the installed app / Android app start at
  `/discover`.
- **Resolution order** (`src/i18n/config.ts` `resolveLocale`): the `lm_locale`
  cookie -> `profiles.ui_language` (so the choice follows the account to another
  device) -> `Accept-Language` -> English. A browser with no cookie but a signed-in
  account gets the account's language from the server, and `LocaleSync` stores it
  as the cookie.
- **Messages** live in `src/i18n/messages/<code>.json`, nested by area (`nav`,
  `auth`, `settings`, ...). `en.json` is the source of truth; any key missing from
  another language shows the English text (`mergeMessages`), and an unknown key
  shows the key itself rather than crashing.
- **Typed keys.** `MessageKey` (`src/i18n/messages.ts`) is derived from `en.json`,
  so `t("nav.discoverr")` is a TypeScript error.
- **Server Components:** `const t = await getT(); t("settings.title")`.
  **Client Components:** `const t = useT(); t("settings.title")`.
- `<html lang>` follows the locale. Dates and numbers should use `Intl` with
  `useLocale()` / `getLocale()`.

### Trade-off: pages render per request

Reading the language cookie in the root layout makes every page render on each
request instead of being served as a static file. The auth proxy already runs on
every request and nearly every page is signed-in and dynamic anyway; the only
pages that lose static prerendering are the landing, login and signup pages. If
that ever matters, the alternative is to keep those pages English-only or to move
the choice into a client-only layer.

## Add or change a string

1. Add the key to `src/i18n/messages/en.json` under the right area.
2. Add the same key to every other file (`tr.json`). Placeholders must match:
   `"Hello {name}"` in both.
3. Use it: `t("area.key")`, or `t("area.key", { name })`.
4. `npm run i18n:check` (also run in CI) fails if a file is missing a key, has an
   extra key, or its `{placeholders}` differ from English.

### Plurals

Write one key per plural category, sharing a base name, and pass `count`:

```json
"inbox": { "unread_one": "{count} unread message", "unread_other": "{count} unread messages" }
```

`t("inbox.unread", { count })` picks the form with `Intl.PluralRules`. Languages
may have different categories (Turkish has `one` and `other`; others may add
`few`, `many`); the check compares base keys and placeholders, not categories.

## Add a language

1. Add the code to `LOCALES` and its own-language name to `LOCALE_NAMES` in
   `src/i18n/config.ts`.
2. Copy `en.json` to `src/i18n/messages/<code>.json` and translate it.
3. Import it in `src/i18n/messages.ts` (`SOURCES`).
4. `npm run i18n:check`, `npm run typecheck`.

The database only checks the *shape* of `profiles.ui_language`
(`supabase/migrations/999995_ui_language.sql`), so no migration is needed.

## What is translated today

Navigation (bottom bar and side rail), Settings, Login and Signup. Everything
else is still English; translating the rest is the follow-up issue (#35).
